# Boa Voice：基于官方 App 的修改与增强清单

**版本：0.1 评审草案｜日期：2026-10-21｜范围：先明确改什么，再冻结接口，最后开发。**

本文作为定制需求入口；更细的模块接口见 [模块与协议设计](../superpowers/specs/2026-10-21-boa-voice-module-protocol-design.md)。当前 Beta 3 维持原状，本轮只补文档。

对照基线是本仓库引入的官方 App 源码快照（`a756cc3`）和当前 Boa 桌面/存储代码（`d2b4582`）。没有重新核验官方线上 App 的最新行为；“源码已有”不等于对应后台已开源、已部署或已在我们的服务上跑通。

## 1. 先回答：哪些协议要改？

**主要改 App 的配置、业务接口与数据策略。自定义 endpoint、权限和存储，本身不需要修改 Clip 固件协议。**

| 层次 | 本轮建议 | 原因 |
| --- | --- | --- |
| Clip BLE AT / Wi-Fi UDP 协议 | 保留；App/SDK 补兼容与联调 | 设备负责录音与文件传输，不负责我们的账号、云存储和模型选择 |
| 官方手机 App 的业务 HTTP API | 用适配层接入自有能力；按需扩展 | 不能只换地址：账号、OSS、ASR、LLM 的路径、鉴权和数据格式必须有对应实现 |
| Boa 已有音频存储 HTTP v1 | 保持兼容；新能力另立契约 | 当前上传、校验、Range 下载可继续复用，不为接手机 UI 直接破坏它 |
| App 内模块接口 | 补齐配置、权限判断、存储和 AI 任务边界 | 页面不应直接决定文件去向、拼鉴权头或选择供应商协议 |

只有未来设备新增命令、返回字段或传输机制时，才评审固件协议扩展；需要同时给固件、SDK、App 定版本与兼容样例。现有 `msg` 错误字段、应答匹配等问题先在适配层解决，具体见 [设备契约差异表](../contracts/clip-device-v1.md)。

## 2. 定制功能总表

P0 为独立可控版本的基础，P1 为完整工作流增强，P2 为按需求扩展。优先级是建议，尚非实施排期。

| 编号 / 优先级 | 修改项 | 官方快照 / 我们当前已有 | 我们要改或增强什么 | 负责位置 / 协议影响 |
| --- | --- | --- | --- | --- |
| C-01 / P0 | 自定义 endpoint | 手机端有多组编译配置；桌面有运行时存储地址/token | 设置页统一管理服务档案，区分业务、认证、存储、ASR、LLM、升级源 | App 配置；增加能力协商契约，不改 BLE |
| C-02 / P0 | 本地模式与自有认证 | 手机端有 SenseCraft/self-hosted 认证抽象，默认 SenseCraft；桌面存储用单用户 token | 本地录音/播放/Clip 基础功能不强制官方账号；自建连接按服务认证 | App 路由/会话；自有认证按需新增 |
| C-03 / P0 | 权限与数据发送控制 | 已有系统权限页；现有自建服务只校验共享 token | 分开系统权限、发送策略、服务端资源授权；可关闭上传和模型处理 | App 策略 + Server 强制执行；需业务契约 |
| C-04 / P0 | 存储控制 | 官方手机有 OSS 上传接口；Boa 有本地库、分片 HTTP 存储和自动备份 | 明确存哪里、何时上传、保留多久、删除哪一份；私有下载与目标隔离 | App 存储适配 + Server；保持 v1，扩展另定义 |
| C-05 / P0 | 凭据与目标隔离 | 各认证链路分别存在；桌面 token 存私有明文文件 | 不跨目标复用 token；配置导出/日志不带密钥；定义吊销与失效处理 | App 凭据模块 + Server；不改设备协议 |
| C-06 / P0 | 手机与桌面复用 | 手机功能模块较全，桌面入口已有录音/库/备份/Clip 控制 | 复用核心业务和适配器，分别做布局与系统权限接入 | App 内接口；手机接入自建存储仍待做 |
| C-07 / P1 | 自选语音/文本模型 | 手机源码已有 ASR、LLM 配置页、远程配置 API 和模板 | 增加本机保存配置、直连/代理执行选择、Azure 等明确协议适配 | App 模型适配；代理执行才需后台任务 API |
| C-08 / P1 | 同步与任务中心 | 桌面已有队列、恢复、重试与进度 | 汇总 Clip 下载、备份、转写、摘要；取消、失败原因、网络切换可见 | App 任务接口；设备下载先按原协议验证 |
| C-09 / P1 | 内容与数据可迁移 | 手机已有转写/摘要相关模块；桌面未接入 | 转写编辑、摘要/待办模板、导出；保存模型、模板和结果版本 | App 领域数据；跨端同步后再定义服务器元数据 API |
| C-10 / P1 | Clip 完整工作流 | 官方 SDK/手机有设备传输与 OTA；桌面尚未接全 | 接入 BLE/Wi-Fi 下载、音频解码、状态同步；危险操作确认 | App/SDK；真机验收后决定是否需固件修复 |
| C-11 / P2 | 更新与运维 | 手机有 Android 直装更新检查代码；桌面尚无完整自动更新 | 自有 Beta 更新源、版本兼容、脱敏诊断；App 与固件升级分开 | 发布服务 + App；独立于音频/设备控制协议 |
| C-12 / P2 | 多人使用 | 当前自建存储无账号/租户隔离 | 账号、资源所有权、分享、配额、审计 | 需要 Server 身份与数据模型，不能靠 App 隐藏按钮实现 |

## 3. 自定义 endpoint：从“改地址”变成“切换可控服务”

### 3.1 现有入口与要改的地方

| 服务类型 | 当前源码入口 | 定制建议 |
| --- | --- | --- |
| 业务服务 | `API_BASE_URL`，默认指向 SenseCraft Voice | 增加运行时服务档案与协议类型，不能假设任何服务器都兼容官方 API |
| 认证服务 | `AUTH_BACKEND`、`AUTH_BASE_URL`，与业务地址独立 | 本地模式 / 自建认证 / 可选官方认证分开；切业务地址不能仍静默使用旧账号链路 |
| 音频存储 | 手机 `UserApi` OSS 接口；桌面独立地址/token | 统一入口展示实际目标，底层选 `boa_http_v1` 或后续验证的适配器 |
| ASR / LLM | 手机配置通过业务后端 API 读写/执行 | 增加明确的本地档案与执行位置，模型服务地址不等于业务服务地址 |
| 固件与升级 | PaaS 有 `PAAS_BASE_URL`；App 更新有 `APP_UPDATE_BASE_URL` | 单独管理信任源与开关；换业务地址不自动更换固件来源 |
| 反馈与其他外发 | 独立反馈入口等 | 明确是否启用；自有模式不依赖官方反馈、模板分享等非必需服务 |

### 3.2 服务档案要定义的字段（建议）

`profileId`、显示名、服务用途、`protocolKind`、根地址、`credentialRef`、`revision`、连接检查结果；存储使用独立 `destinationId`，模型使用独立 `modelProfileId`。凭据引用不等于明文密钥。

- URL 路径规则按协议验证：现有 `boa_http_v1` 只接受根地址；模型地址可以有供应商要求的路径，不能套用同一个 URL 拼接规则。
- 测试连接分成网络可达、鉴权通过、协议兼容、能力可用；一个 HTTP 200 不代表四项都通过。模型测试需说明可能产生请求与费用。
- 配置保存失败不显示成功。更换地址/身份形成新的目标版本，旧任务保持原目标，禁止自动投向新地址；是否迁移历史副本由用户明确选择。
- 新增可选服务能力查询：建议 `GET /api/boa/v1/capabilities`，声明协议版本、支持动作、文件大小限制和认证模式。**当前没有此接口**；旧存储可由用户显式选择 v1，不能把查询 404 自动当成“所有能力可用”。
- 自有模式所需请求只去配置的目标；失败不回退到官方云。对象预签名 URL、模型服务、固件下载各用自己的请求与鉴权规则，不把业务 Bearer token 附加到外域或重定向。
- 保留本机/受信局域网 HTTP 调试，远程服务采用 HTTPS；不通过关闭证书验证解决连接问题。

**验收：**换成自己的服务后可录音、上传、下载、播放；抓取脱敏网络记录确认没有非预期官方依赖；切换服务不会串账号、串任务或误标已备份。

## 4. 权限控制：必须分三层

| 层次 | 控制什么 | 执行者 | 拒绝后的行为 |
| --- | --- | --- | --- |
| 系统权限 | 麦克风、蓝牙、所需本地网络/文件目录权限 | iOS / Android / macOS 系统；App 按需请求 | 给出具体入口与原因；不影响已授权的离线功能 |
| 数据操作策略 | 自动备份、允许把音频发到哪个 ASR、是否允许云端摘要 | App 流程与任务模块 | 未允许则不创建外发任务；不因系统麦克风允许就视作允许上传 |
| 服务端访问权限 | 谁可读、写、删除哪份资源，能否调用付费模型/修改配置 | Server 按每次请求鉴权、资源归属与策略校验 | 返回明确未认证/无权限，App 更新状态；不能只隐藏入口 |

个人版先保留“纯本地 + 自建单用户 token”即可，不必先做复杂组织角色。**现有共享 token 代表同一个拥有全部现有存储接口访问权的身份，不具备只读、删除限制或用户隔离。**

建议先冻结动作词汇，后续再映射 API：

| 动作 | 个人版行为 | 需要 Server 新增什么 |
| --- | --- | --- |
| `audio.read` / `audio.upload` | 本地操作不需要服务器账号；远程操作需要有效服务凭据 | 若要只读 token，增加 scope 与逐路由校验 |
| `audio.delete_remote` | 默认不开放，当前服务无成品删除接口 | 资源归属、删除 API、幂等与回收约定 |
| `ai.transcribe` / `ai.summarize` | 用户选择目标后显式执行；自动处理单独开关 | 直连由供应商校验凭据；代理模式须检查权限及配额 |
| `settings.manage` | 自用允许修改本机设置；服务要求不能被本机开关放宽 | 多人部署时增加管理授权与策略版本 |
| `device.control` / `device.update` | App 提供操作边界与危险操作确认 | 云端账号权限不等于 Clip 已具备相同的设备端访问控制 |

建议新增 Policy 模块（尚未实现）：`evaluate(action, resource, target) -> allow / deny / requireConfirmation + reason`，由用例调用，不散落在各按钮里。服务下发的策略与本机选择取更严格结果；后台独立执行同样的服务权限检查。`capabilities` 只描述功能，不代表当前用户拥有权限。

系统权限状态可刷新；凭据过期要暂停相关任务。明确的写入失败与结果未知分开处理，不能让未经确认的请求无限重试。撤回外发许可后停止新任务和待发送队列；已发送给服务器/供应商的数据需通过各自删除机制处理，不能声称关闭开关即可撤回。

**验收：**拒绝麦克风仍能播放；关闭自动上传后新录音不自动发送、仍可手动上传；无效 token 无法读远程文件；未来只读 token 在绕过 UI 直接调用上传时也必须被拒绝。

## 5. 存储控制：明确每一份文件在哪里

### 5.1 要给用户哪些选项

| 控制项 | 当前状态 | 建议增强与默认边界 |
| --- | --- | --- |
| 本地录音与库 | 桌面沙箱保存、独立复制入库 | 保留原件；导出目录与内部库分开，目录迁移需要平台授权与校验 |
| 自动上传 | 已有开关和手动上传 | 保留既有选择；新目标先确认，展示目标与排队条件，配置缺失只本地保存 |
| 上传时机 | 桌面有恢复队列 | 增加按网络/文件来源的策略；设备热点无外网时等待，录音未封口不上传 |
| 本地/远程关系 | 已有仅本地/仅服务器/两端都有及未确认状态 | 每个目标分别记录，刷新失败不能当远程已删除；下载后校验再允许离线播放 |
| 存储后端 | 当前自建服务使用磁盘 + SQLite | 后续可增加 S3/OSS/MinIO 适配；bucket/prefix 和主密钥配置在服务端 |
| 数据保留 | 本地回收/恢复，远程成品没有自动清理接口 | 本地缓存、原件、远程副本分别设置期限；先估算影响，不自动删唯一可用原件 |
| 删除语义 | 本地回收不删除远程，远程无成品删除 | 明确“仅本地 / 指定远程 / 两者”；远程失败显示部分完成，不静默扩大删除范围 |
| 配额与空间 | 有文件大小限制和写入错误 | 展示本机/服务剩余空间、文件大小限制；多人阶段再加用户配额 |
| 隐私与恢复 | token 鉴权，未实现端到端加密 | 私有访问、过期下载凭据、备份恢复说明；加密需求另行设计，不把文件权限当加密 |

### 5.2 官方上传接口和我们的接口并不相同

| 流程 | 官方快照中的手机客户端 | Boa 当前服务 |
| --- | --- | --- |
| 小音频上传 | ≤5 MiB：multipart `POST /api/v1/oss/upload` | JSON 创建 `/api/audio/uploads`，再 PUT 二进制分片 |
| 大音频上传 | `/api/v1/oss/upload/init`、`chunk`、`complete` | `/api/audio/uploads/{id}/parts/{index}`，带 SHA-256；complete 后轮询 |
| 预签名上传 | `UserApi` 中头像使用 `/api/v1/user/presignUpload` 再 PUT | 当前无预签名上传；不能把头像流程概括为所有音频流程 |
| 下载与数据身份 | OSS 返回的地址/对象信息与手机业务记录关联 | 远程 id、长度、SHA-256；带鉴权 GET/HEAD 内容与 Range |

**推荐：App 通过 Storage 接口接入 `boa_http_v1`，不为了复用页面立即重建整套官方账号/OSS/ASR 后台。** 如果以后确实要让原手机上传流程零改动接入，再单独做官方 API 兼容层，不能让两套协议名称相同但语义不同。

未来接对象存储时：App 向自有服务申请上传会话 → 按返回的 URL/指定头上传 → 服务核验对象与提交状态 → App 才显示成功。永久身份用远程 id/objectKey/内容校验信息，不把会过期的下载 URL 当文件 id；下载时鉴权申请临时 URL。此流程是后续设计，当前未实现。

**验收：**大文件中断可恢复、下载哈希一致且可播放；本地删除不误删服务器；换目标不会显示旧目标已备份；保留策略不删除唯一原件；服务备份恢复后文件及清单一致。

## 6. 模型与内容处理也要可控

原手机源码已有模型选择、配置编辑和 Prompt 模板，值得复用 UI 和领域模型；但其远程配置 API 会将 `config_json` 发给业务后端。**“本地配置模型”要明确配置是否离开本机，不能沿用远程保存却声称只在本地。**

建议第一阶段选择本机调度、用户自带凭据（BYOK）：

- 语音识别与摘要分开配置，可分别选供应商、地址、模型和凭据；需要的 Azure deployment、API version 等按协议类型定义，不只增加一个名为 Azure 的选项。
- Azure Speech、Azure 模型语音接口和文本模型分开适配；仅填写 endpoint 不代表任意 API 互相兼容。具体字段按选定服务的正式契约确认，本轮不指定某个在线模型版本。
- 直连模式：配置保存在本机，音频/文本发送到明确选定的模型目标；自建文件存储不自动得到模型密钥。代理模式：配置/凭据托管在自有服务，必须另行实现与说明。
- 长录音分段、时间轴、进度、取消、失败重试由任务层处理；原始音频不被转码结果覆盖。摘要绑定转写版本和模板版本，可重跑、可导出。
- 原手机远程配置功能需要显式切换适配器；桌面目前尚未接入转写/摘要。首期不承诺“设备直连模型”或“后台已部署”。

**验收：**无 Clip 也能录音 → 保存 → 用户选模型转写 → 摘要 → 导出；全程可看见发送目标；断网不丢原音频；原配置密钥不出现在日志或导出的配置中。

## 7. 实现前必须冻结的接口清单

下面是下一步要评审的边界，并非已经实现的新 API；具体函数与 DTO 以 [模块设计](../superpowers/specs/2026-10-21-boa-voice-module-protocol-design.md) 为基础补充。新增 Policy 边界需在该设计下一版同步。

| 边界 | 需要先定义什么 | 不能混淆什么 |
| --- | --- | --- |
| Configuration → 各适配器 | 服务用途、协议类型、profile/目标版本、凭据引用与测试结果 | 一个 baseURL 不代表认证/存储/模型/升级共用服务 |
| Application → Policy（新增建议） | action/resource/target、允许/拒绝/确认、策略版本 | 本机策略不授予服务器访问权 |
| Application → Sync → Storage | 上传目标、手动/自动触发、状态、完整性、恢复、删除范围 | 上传进度 100% 不等于服务校验完成 |
| Application → AI Jobs → ASR/LLM | 执行位置、输入版本、模型档案、结果、取消与费用边界 | 选择模型不等于授权上传全部录音 |
| Application → Device | 已有命令白名单、状态快照、传输文件与错误 | 云端权限不能替代设备协议或证明真机兼容 |
| App → Server | 保留存储 v1；能力查询、细分授权、私有对象存储、远程删除分别定义 | 当前共享 token 服务不能宣称已有账号权限系统 |

不先铺开几十个新 HTTP 路由。先确定每项的请求/响应、鉴权、资源身份、错误、幂等、版本和验收样例；保持既有存储 v1 的格式与语义。新增控制接口采用独立版本命名，是否复用官方接口逐项决定。

## 8. 建议推进顺序

1. **先评审改造范围：**C-01～C-06 为基础；确认本地模式、自有服务、不强制官方账号这条主线。
2. **再冻结三个协议包：**服务配置/能力、权限与数据策略、存储与副本生命周期；写出成功、拒绝、断线、切目标的样例。
3. **实施基础改造：**统一手机/桌面配置与 Storage 适配，跑通本地录音、上传、下载、播放；每完成一项更新验收记录。
4. **补模型与 Clip：**接选定模型和内容处理，硬件到位后完成原有设备命令、下载与音频解码联调。
5. **交付时再打 Beta DMG：**本地验收后统一打包；多人权限、对象存储和自动更新按实际需求单独推进。
