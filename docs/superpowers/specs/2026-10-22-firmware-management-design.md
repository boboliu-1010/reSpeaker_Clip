用户已选择首版同时包含 **自建 Server 固件库、版本分发、权限管理和 App 手动升级**。本文件是实施前的产品与模块设计，不表示这些新增功能已经实现；沿用“先定义协议和模块接口”的要求。HTTP 与应用接口见 [固件管理契约](../../contracts/firmware-http-v1.md)。

## 1. 当前事实

| 位置 | 已有能力 | 与目标的差距 |
| --- | --- | --- |
| 手机业务 App | `FirmwareUpdatePage` 有官方云检查更新、本地 zip/bin 选择、BLE OTA 及进度 | 面向 SenseCAP PaaS；不是自建固件目录与权限系统 |
| Flutter SDK | `OtaSession` + `OtaFirmwareProcessor`，SMP/mcumgr BLE 升级、多镜像解析 | 默认 `eraseAppSettings: true`；现有解析不能视为完整的兼容性和发行者验证 |
| macOS 依赖 | 锁定 mcumgr_flutter 0.8.1 声明 macOS 支持，桌面插件已注册 | 不等于本项目桌面真机 OTA 已验收 |
| Boa 桌面 | Clip 连接、状态与固件版本显示 | 无固件库、包管理、升级流程和升级记录入口 |
| 固件源码 | `applications/clip/prj.conf` 启用 BLE OTA；配置两个可升级镜像；仓库有 USB MCUboot 恢复说明 | 实物刷入包、签名信任、槽位/确认策略和配置保留仍须逐 profile 联调 |
| 自建 Server | 9528 HTTPS `/api/audio` 存储，当前单用户音频令牌 | 没有固件目录、发布、固件角色或升级授权 API |

依据为本仓库源码和已安装锁定依赖，不将旧记忆中的 AP 固件限制套到现有 STA 实验分支。升级包不属于录音，不进入 `/api/audio/recordings`。

## 2. 产品流程与页面

入口：桌面和手机的 **设备 → 固件管理**；桌面另可从设置进入固件库，不要求先连设备才能浏览。

| 页面/区域 | 首版行为 |
| --- | --- |
| 设备固件 | 当前版本、板型/profile、连接状态、最近读取时间、升级能力；缺失值显示未知 |
| 固件库 | 本地/服务器来源、版本、beta 渠道、profile、构建提交、大小、校验值、发布状态；支持过滤与缓存 |
| 固件详情 | 更新说明、适用硬件、镜像构成、配置迁移/数据影响、签名验证结果；区分“已缓存”和“已安装” |
| 发布管理 | 管理员导入 zip/signed.bin、补充元数据、校验、发布/撤下；未校验包只在隔离区可见 |
| 升级向导 | 选择目标、兼容性检查、影响确认、申请授权、下载校验、BLE 升级、重连复核 |
| 升级记录 | 操作人、设备、旧/目标镜像、阶段、时间、结果、失败原因、恢复指引；断开后结果可为待确认 |
| 服务与权限 | 自定义固件 Server endpoint、凭据引用、连接测试、当前角色及设备范围 |

首版全部使用 **beta** 渠道。官方、Roger、自定义表示构建来源，不能替代硬件兼容 profile、签名信任或已验证标记。不会因版本号看起来更大就跨 profile 推荐更新。

## 3. 模块职责

```text
App UI → FirmwareUseCases → FirmwareCatalogPort → 自建 Firmware API
                         → FirmwareCachePort   → 本地隔离缓存
                         → DeviceUpdatePort    → SDK / BLE SMP → Clip
Server Firmware API → FirmwareAuthorization → PackageStore / Validator / AuditStore
```

- Server 保存固件制品、元数据、发布状态、访问范围、授权和审计；不替 App 连接蓝牙。
- App 下载并校验包，申请授权，管理设备操作互斥与本机升级生命周期，展示真实状态。
- 设备/bootloader 执行镜像接收、验证、切换与确认，仍是镜像签名和启动策略的最终边界。
- `FirmwareCache` 与音频库、回收站、音频同步队列分开；固件缓存不能当作设备备份。
- 保留现有 `/api/audio` 行为和凭据。固件 API 使用独立授权；旧音频 token 不能自动获得固件发布权限。

## 4. 权限与存储

| 角色 | 浏览/下载已授权固件 | 授权设备升级 | 导入/发布/撤下 | 管理角色与信任策略 |
| --- | --- | --- | --- | --- |
| viewer | 是，限定可见范围 | 否 | 否 | 否 |
| operator | 是 | 是，限定设备/profile | 否 | 否 |
| admin | 是 | 是 | 是 | 是 |

首版使用独立可撤销的高熵 Bearer 凭据，由受控管理命令创建/轮换，Server 只保存校验摘要；不把现有音频 token 升格成管理员。App 保存 credentialRef，不在日志、导出或固件清单中保存秘密。凭据持久化复用现有抽象，不能顺带重置钥匙串或音频设置。

管理员分配 `device_ref` 与允许的 profile；手机/macOS 的 BLE remoteId 只属于本机连接标识，不作为跨客户端设备身份。实物稳定身份获取方式未验证前，仅允许操作者现场核对的手动升级，不开放远程无人值守部署。

Server 权限约束自建服务和本 App 的操作；不能保证持有设备、有效镜像和其他刷机工具的人无法绕过 App。要在设备侧强制发行者控制，需要实际 bootloader 签名策略，不能仅靠 UI 权限。

固件数据使用独立数据目录、数据库/表及 blob 存储，沿用磁盘方案，暂不引入 S3。第一版默认包上限 32 MiB、解压总量 64 MiB、归档条目 32 项、镜像 1–2 个、固件库配额 2 GiB，均由 Server capabilities 下发；这些是建议产品限制，不是硬件参数。已发布包不可覆盖；撤下不自动删除设备或历史记录。垃圾回收不得删除被发布版本、活跃升级或保留审计引用的制品。

## 5. 兼容性与升级条件

1. 发行记录必须固定包 SHA-256、大小、板型、profile、镜像集合、源码提交/构建来源、bootloader/签名策略及配置迁移说明。人工标注和已验证证据分开保存。
2. SHA-256 仅校验内容，不证明发行者可信。未知签名策略或无法确认兼容性的包可隔离保存，但不得发布为“可升级”。不上传签名私钥到 App 或普通固件上传接口。
3. 首版接收 OTA zip 和有效 signed.bin；merged.hex、网络核单独 hex、任意重命名 bin 不作为 BLE OTA 包。单镜像包必须明确 image index，不能无条件当作 image 0；应用与网络核版本组合须匹配。
4. ZIP 提取前限制体积/条目，拒绝路径穿越、绝对路径、链接、重复/冲突镜像与解压炸弹；必须逐镜像校验大小、哈希和镜像结构。服务端检查后 App 再检查实际下载字节。
5. 启动前重新读取设备状态。录音、暂停录音、设备文件传输、直传上传或其他升级活动时阻止启动；状态未知不当作空闲。操作锁由 Device 模块持有，不由页面按钮各自判断。
6. 电量、供电、可用槽位及 bootloader 条件取已验证 profile 的策略；首版建议电池至少 30% 或满足经验证的外接供电条件。未知/不满足时阻止，不能因为插线就跳过全部检查。
7. 默认不擦除应用设置，不格式化、不恢复出厂、不删除录音。现有 SDK 的 `eraseAppSettings: true` 不能直接沿用；保留 Wi-Fi/HTTPS endpoint/token/证书的实际支持必须验收。涉及擦除或迁移的版本必须单独说明并阻止无意升级。
8. 同版不同哈希表示不同构建；降级、跨 profile、修改信任策略均需管理员策略和额外确认。bootloader anti-rollback 是否允许仍以实物为准，不能承诺“任意回滚”。

## 6. 设备升级与恢复

```text
检查目标 → 申请授权 → 下载 → 完整性/兼容性检查 → 最终状态复核
→ 获取设备独占锁 → BLE SMP 传输 → 镜像验证/测试 → 重启
→ 重连读取运行镜像与版本 → 确认 → 成功 / 失败 / 待确认
```

- 下载 100%、SMP 上传结束、SDK 回调成功、设备新镜像已运行，是不同事件。只有确认所需镜像已运行并满足 profile 的确认条件，UI 才显示升级成功。
- 第一版复用 BLE SMP，服务 UUID `00001530-1212-EFDE-1523-785FEABCD123`；不新增 AT 固件上传命令。BLE 控制/轮询与 SMP 会话的切换由适配器统一编排。
- `AT+DFU` 是进入 USB 恢复模式的相关路径，不能当作普通 BLE OTA 的必要前置命令。USB 恢复首版提供检测/指引，自动调用外部刷机工具另行定义，不开放任意 shell 命令输入。
- 下载/准备阶段可取消；测试、重启、确认等关键阶段不承诺强制取消安全。异常退出后先查设备镜像状态，不自动重放 reset/confirm，也不直接重刷。
- 支持续传与回滚仅在该 profile、bootloader 和 SDK 经联调确认时显示。无法确定升级结果记为 `needs_attention`，保留制品和恢复指引。
- Clip 已联网并能上传录音，不表示能自行下载和安装固件。Server → Clip 直接 OTA、批量远程推送、静默自动安装不在本版范围，需独立固件设计。

## 7. 实施拆分与验收门槛

| 交付 | 内容 | 完成证据 |
| --- | --- | --- |
| A：契约与固件基线 | 确定实际包、profile、签名/槽位、设备身份及配置保留策略 | 样例清单、来源校验、协议评审；未知项明确阻止升级 |
| B：Server 固件库 | 授权、隔离导入、校验、发布、分发、撤下与审计 | 权限反向测试、损坏/恶意归档测试、幂等/重启/持久化测试 |
| C：App 管理 | 本地/远程列表、下载缓存、详情、发布管理和授权预检 | 无设备可测管理流程；离线/过期授权/篡改包均正确处理 |
| D：设备 OTA | 桌面接入并统一手机适配，独占锁、进度、复核、恢复 | Android/iPhone/macOS 按 profile 真机记录，不能用模拟器代替 |

交付顺序是依赖关系，不是缩减用户选择的首版范围。Server 可先在开发机 9528 与音频 API 共存，独立目录和授权；现有音频上传/下载回归必须通过。硬件到位前可完成管理能力与故障模拟，不宣称 OTA 真机完成。本次只生成评审文档，不部署新 API、不创建真实管理员令牌、不刷机、不发布安装包。
