# 固件管理：功能与协议调整清单

**日期：2026-10-22｜状态：接口调整已纳入 draft.3，产品/工程核实项仍保留，未开发。**

这份文档先用产品语言列出要做什么、建议怎么做，再列需要补齐的接口。你可以直接按编号批注，例如“F-05 要支持 USB 正常升级”“F-07 允许离线升级”。没有意见的条目不必逐项回复。用户随后要求按协议和 endpoint 方案修订，A-01～A-08 已写入 draft.3；这不表示全部 F 产品选项或硬件事实都已自动确认。

详细参考：[固件管理设计](../superpowers/specs/2026-10-22-firmware-management-design.md) · [HTTP 与模块接口草案](../contracts/firmware-http-v1.md)。阅读顺序建议：先看 [统一总览](boa-voice-overview.md)，本清单和接口仅作开发附录。

## 1. 已明确的范围

以下来自已有要求，本次不缩减：

- App 要有固件管理，首版同时包含自建 Server 固件库、版本分发和权限管理。
- 固件来源、服务地址和数据由我们控制，不依赖只有官方账号才能使用的流程。
- 当前均按 beta 管理，开发环境使用既有开发机；部署新模块前仍须验证兼容性。
- 先定义模块接口和协议，再开发。设计草案不等于已实现，管理流程测试不等于设备 OTA 真机测试。

## 2. 首版用户操作应该是什么样

| 操作人 | 操作流程 | 用户最终能看到什么 |
| --- | --- | --- |
| 开发者 | 后台导入 → 校验 → 补说明与适用设备 → 发布/撤下 beta | 用户看到可追溯的兼容版本 |
| 用户 | 连接自己的 Clip → 查看版本与影响 → 确认升级 → 查看结果 | 本人设备进度、结果与恢复指引 |
| 开发者 | 升级异常 → 核实设备 → 审计归档 | 不自动重刷或无证据解锁 |

## 3. 建议逐项确认的产品规则

### F-01 服务地址与官方依赖

**建议：**在 App 里配置自己的固件服务，默认可与音频服务部署在同一台机器。固件和音频分别校验协议与动作/归属，复用统一用户身份；不因为地址相同就把音频 token 当作固件开发者 token。自建服务失败不自动切到官方云。

**影响：**自用时可以填同一个 Server 根地址，不需要搭两台服务器；原 `/api/audio` 保持兼容。当前 9528 已部署的是音频服务，不能把它写成已经具备固件 API。

### F-02 固件从哪里来

**建议：**开发者在后台导入官方、Roger 或自己的构建包，再上传到自建固件库。记录来源仓库、提交、构建标识、文件哈希和说明。首版不自动抓取第三方网站或跟随 GitHub 的 latest 下载地址。

**影响：**能自己控制版本；每个包都要明确来源和兼容范围。“来自官方/Roger”是来源标签，不等于这个包已经适配当前设备。

### F-03 两类角色与用户隔离

只保留 user（用户）和 developer（开发者）。用户管理自己的录音、设备和结果，可手动安装适用的已发布固件；开发者维护模型、任务、固件发布、策略和服务。不再采用 viewer/operator/admin 或主体 grants 矩阵。

Server 每次校验 owner_user_id；统一用户身份贯通音频、AI、设备和固件，不另建固件账号。现有共享 token 仍是单用户模式，尚未具备隔离。

### F-04 管理功能放在哪里

用户 App 只展示自己的设备、内容、处理结果与兼容固件。包导入/发布、模型密钥、策略和用户管理放开发者后台/受控 CLI。后台任务由开发者开发维护、Server 自动运行，不要求开发者逐条手工处理。

设备预登记和维护保留在固件附录；用户绑定证明与解绑协议在统一 Device 模块另行冻结，不能凭 BLE 地址或任意 ID 接管设备。

### F-05 用什么方式升级

**建议：**首版普通升级走 App → BLE SMP → Clip，复用现有 SDK。USB 提供恢复指引；USB 正常升级界面、Server 直接推送到 Clip、设备自行联网下载固件分别列后续能力。

**源码核对后新增约束：**[Roger 的 HTTPS 实验构建主动拒绝应用 DFU](../development/2026-10-22-roger-firmware-upgrade-inspection.md)，当前集成基线也如此。因此 BLE 首版是目标，需先进行固件改造/验收；现有维护路径是 bootloader USB recovery，不能只把手机 OTA 页面搬到桌面就宣称可用。

**需要留意：**如果你希望 Mac 首版就能插 USB 完成常规升级，需要把它明确加入首版，将增加 USB 端口、外部工具/原生适配器和恢复状态接口。Clip 现有联网录音上传能力不等于已实现联网 OTA。

### F-06 是否自动安装

**建议：**App 可检查新版本、提示并缓存包，但安装必须手动确认。首版不强制更新，不定时静默刷机，不因接入电源自动升级。

**影响：**升级不会突然打断录音。未来如果增加无人值守更新，需要单独定义调度窗口、供电、业务互斥和恢复策略。

### F-07 是否允许离线升级

**建议：**离线时可查看已缓存的固件和记录；首版启动新升级仍需在线确认权限和版本状态。已经开始的设备关键阶段遇到断网，不强行中止，完成后再补报。

**取舍：**规则简单，撤下和撤权能及时生效；但没有网络时，即使已缓存包也不能新刷机。如果需要离线升级，应另定可离线验证的授权、有效期和撤销边界，不能只加一个“跳过授权”开关。

### F-08 升级后保留什么

**建议：**常规升级要求保留录音、Wi-Fi、上传地址、上传凭据、证书及设备设置；涉及迁移或擦除的包单独标记并阻止误升级。保留能力未知时不能显示“不会丢数据”。

**已知差距：**当前 SDK 的默认升级配置为 `eraseAppSettings: true`，需要显式处理，不能直接复用默认值。关闭此选项是否足够保留所有配置，仍需实际固件验证；不把 App 本地音频副本当作设备配置备份。

### F-09 能不能任意换版本或回滚

**建议：**默认只提供同硬件、同 profile 的兼容版本。AP/UDP 构建与 STA/HTTPS 构建分开标识；版本号相同、哈希不同，也视为不同构建。降级或切换 profile 需要开发者策略和明确提示。

**影响：**不提供未经验证的“一键回滚”。是否能降级、是否自动恢复旧镜像，取决于真实 bootloader、镜像和槽位配置，不由版本列表决定。

### F-10 什么样的包能发布

**建议：**接收经过检查的 OTA ZIP 和 signed.bin；HEX/完整烧录包不混入 BLE OTA 列表。先校验体积、镜像结构、逐镜像哈希、适用设备和签名信任，再发布；不符合条件的包留在隔离区供开发者查看。

**影响：**本地导入不等于可刷入，SHA-256 只能证明字节一致，不能证明来源可信。签名私钥不能放进 App 或普通上传接口。实际信任公钥、板型和多镜像映射是工程核实项。

### F-11 撤下、删除和空间清理

**建议：**发布后的包不可覆盖。发现问题先撤下，阻止新下载/新升级；保留历史和活跃升级所需字节。清理废弃上传、未引用缓存与审计保留是不同操作。

**影响：**“撤下版本”不代表已经从设备卸载，也不应删除正在使用的镜像。包大小、解压限制、配额和保留期先作为可配置策略；草案里的 32 MiB/64 MiB/2 GiB 是建议默认值，不是已确认硬件限制。

### F-12 怎么判断升级成功，失败后怎么办

**建议：**下载完、传输完、重启和确认新镜像运行分别展示。升级后重新读取运行镜像和版本；结果不确定就显示“待确认”，保留恢复指引和操作记录。

**影响：**不按进度条 100% 直接报成功。对 App 上报的结果标明证据来源，不冒充设备签名证明。关键阶段不提供未经验证的“强制取消”；重复进入页面也不能自动重新刷写。

## 4. 已纳入 draft.3 的接口调整

下表保留 draft.1 的问题及处理方向；用户要求按此方案修订后，A-01～A-08 已统一写入 [draft.3](../contracts/firmware-http-v1.md) 的接口表、DTO、状态/竞争规则与 JSON 示例。这里的“已纳入”仅指文档，相关 API 尚未部署，硬件条件仍需核实。

| 编号（均已纳入） | draft.1 的问题 | draft.3 调整 | 解决什么问题 |
| --- | --- | --- | --- |
| A-01 开始升级 | 用 `PUT events/0` 同时做审计与开始授权 | 已增加显式 `POST /upgrades/{id}/start`；原子复核权限、版本、策略和设备租约，事件接口只记录进度 | 明确哪个请求允许真正写设备；响应丢失可按同一操作查询/幂等恢复 |
| A-02 取消与结果核实 | 定义了 cancelled/needs_attention，却没有完整取消、核实后的解锁流程 | 已增加独立 cancel 和携带设备观测/原因的 resolve，并明确租约释放条件；关键阶段不把 cancel 当强停指令 | 既不永久占锁，也不因 TTL 到期盲目允许再次刷写 |
| A-03 设备管理 | 设备登记只通过 CLI，日常管理无法完整在 App 做 | GET devices 按归属过滤；POST/PATCH 由开发者维护预登记与兼容策略；用户绑定/解绑协议仍待冻结 | 区分用户设备入口与开发者维护，避免越权和跨平台串设备 |
| A-04 修改权限 | 已有凭据创建/撤销/轮换，缺少修改现有授权范围的具体接口 | draft.3 移除独立 principals/grants；改为两角色与资源归属，身份管理由统一认证模块负责 | 减少重复账号体系，保证用户之间隔离 |
| A-05 profile 与策略 | 发布依赖 policy_revision、签名和兼容 profile，却缺其管理/读取定义 | 已补 profiles、policy 与历史 policies 接口；保留公开信任标识，不接收签名私钥 | 明确策略从哪里来、谁能改，避免由上传文件随意自报兼容 |
| A-06 状态与租约 | 授权状态、升级状态、设备占用状态混在描述里 | 已拆分 authorization_state、operation_state、lease_state 和 reported_phase，列明超时/恢复规则 | 开发者不需要靠猜测决定何时重试、解锁或报成功 |
| A-07 撤下/撤权的竞争 | 需要同时满足阻止新升级和不破坏已开始的关键阶段 | 已补开始前复核、开始后保留快照和镜像、按权限补报或开发者核实规则 | 不因撤销权限、清缓存或撤下版本导致正在执行的升级丢镜像 |
| A-08 endpoint 与缓存 | 自定义地址、主体、包和授权快照需要统一身份边界 | 已固定 endpoint/origin、server_id、principal、release/package/hash 和策略修订，不迁移旧任务 | 防止把 A 服务缓存或授权误用于 B 服务 |

## 5. 哪些必须由工程核实，而不是让你猜

| 核实项 | 需要拿到的证据 | 未明确时的处理 |
| --- | --- | --- |
| 实物板型与运行固件 | 真机版本、构建来源、包哈希与板型 | 不宣称官方/Roger/实验包都兼容 |
| 签名与 bootloader | 实际可信公钥标识、槽位、镜像索引、测试/确认和降级策略 | 可整理/隔离存包，不能当作可升级版本发布 |
| 配置与录音保留 | 升级前后录音校验、Wi-Fi/上传配置仍有效的记录 | 不承诺无损升级；常规升级阻止未知影响包 |
| 设备身份 | 可读的稳定身份，以及 App 本机 BLE 标识到逻辑设备的映射 | 仅现场手动核对，不能据此开启无人值守批量升级 |
| 三端 OTA 与恢复 | macOS、Android、iPhone 的真实升级/断链/重连/恢复记录 | SDK 声明支持不算设备验收，模拟器不算真机 |

以上核实不要求你自行准备协议细节，后续由实现/联调工作逐项给证据。
